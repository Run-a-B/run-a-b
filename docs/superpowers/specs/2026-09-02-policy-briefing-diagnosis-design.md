# 정책 설명 보강 및 60초 정책 진단 설계

## 1. 목표

Run-a-B의 기존 보라색 중심 시각 언어와 정책 상세 레이아웃을 유지하면서 다음 흐름을 하나로 연결한다.

1. 사용자가 정책의 대상·혜택·기간·신청 방법을 빠르게 파악한다.
2. 부족하거나 확인되지 않은 정책 정보는 숨기거나 추정하지 않고 명시한다.
3. 사용자가 약 60초 안에 사업 정보 다섯 항목을 입력한다.
4. 서비스가 입력 정보와 공고 조건을 규칙 기반으로 비교한다.
5. 결과의 각 항목에 사용자 값, 정책 값, 판정, 이유, 정보 출처를 표시한다.
6. 결과에서 원문 확인과 신청 준비로 이어진다.

이 기능은 공식 자격 판정이나 합격률 예측이 아니다. 모든 화면은 “공고문 조건과 입력 정보의 1차 비교”임을 명확히 표시한다.

## 2. 현재 데이터 제약

2026-09-02 로컬 데이터 점검 기준 정책은 1,532개다.

- 모든 정책에 기업마당 외부 ID, 제목, 설명, 지원대상, 원문 상세 URL이 있다.
- 신청 방법은 1,530개에 있다.
- 신청 시작일과 종료일은 각각 636개에 있다.
- 공고번호, 담당부서, 지원 규모, 사업 목적은 모든 정책에서 비어 있다.
- `policy_card`와 `policy_summary`는 비어 있다.

따라서 첫 구현은 기업마당 목록 데이터와 원문 링크만을 사실 근거로 사용한다. 구조화 정책 카드가 있으면 추가 조건을 사용하되, 없으면 `UNKNOWN`을 유지한다. 원문을 직접 인용하거나 상세 공고에서 추출했다고 표현하지 않는다.

## 3. 범위

### 이번 구현에 포함

- 정책 상세의 “한눈에 보기”와 정보 품질 표시
- AI 요약 실패 시 사실 기반 대체 설명
- 공개형 60초 진단 입력 화면
- 규칙 기반 진단 API와 근거 행
- 정책 상세와 정책 목록에서 진단 진입
- 결과에서 원문과 신청 체크리스트로 연결
- 기존 체크리스트의 가짜 데이터 우선 노출 제거
- 공통 준비 서류를 “정책 필수”가 아닌 “일반 준비 권장”으로 교정

### 후속 별도 설계로 분리

- 기업마당 상세 HTML 수집 및 재수집 정책
- PDF/HWP 첨부파일 파싱
- 원문 스냅샷, 내용 해시, 파서 버전, 문장 위치 기반 인용
- 전체 1,532개 정책 백필
- 진단 이력 영구 저장과 정책 비교
- AI가 만드는 보조 서술

상세 수집은 현재 실제 HTML fixture, 필드별 selector, 속도 제한, 실패 복구, 출처 스냅샷 규칙이 없으므로 이번 범위에 억지로 포함하지 않는다.

## 4. 디자인 보존 규칙

새로운 색상 체계나 독립적인 디자인 언어를 만들지 않는다.

- 페이지 배경: `bg-gray-50`
- 기본 카드: `bg-white rounded-2xl border border-gray-200`
- 강조 패널: `bg-primary-50 border-primary-100`
- 기본 행동: `bg-primary-600 hover:bg-primary-700 text-white`
- 내부 행과 입력: `rounded-xl`
- 본문: Pretendard와 기존 gray 토큰
- 데스크톱 여백: `pt-15`, `px-40`
- 상세 화면: 기존 본문·고정 사이드 패널 구도 유지
- 상태색은 기존 green, yellow, red, gray 토큰만 사용

진단 화면도 기존 정책 상세·체크리스트·리포트의 카드, 배지, 진행 상태 표현을 조합한다. 채팅 UI, 유리 효과, 새로운 그라디언트, 네온 효과는 사용하지 않는다.

## 5. 정책 상세 설명 구조

기존 `PolicyDetail`의 정보는 다음 순서로 재구성한다.

### 한눈에 보기

세 개의 동일한 내부 카드로 표시한다.

1. 지원 대상: `targetGroup`; 없으면 `원문에서 지원 대상을 확인해 주세요.`
2. 지원 내용: `supportScale`; 없으면 `지원 금액·방식 정보가 아직 수집되지 않았어요.`
3. 신청 기간: `applicationPeriod`; 없으면 `기간 정보 없음 — 원문 공고 확인`

### 상세 설명

- 사업 내용은 AI 확장 설명이 있으면 표시한다.
- AI 설명이 없거나 실패하면 `purposeText`, `description` 순서의 저장된 원문 필드만 사용한다.
- AI 실패를 “곧 제공 예정”으로 숨기지 않고 `자동 요약을 불러오지 못해 수집된 공고 정보를 보여드려요.`라고 표시한다.
- 신청 방법이 없으면 섹션을 제거하지 않고 `신청 방법 정보가 아직 수집되지 않았어요.`와 원문 링크를 표시한다.

### 정보 품질

다음 정보를 한 패널에 표시한다.

- 출처: 기업마당
- 확인 가능한 항목 수
- 확인되지 않은 항목 이름
- 구조화 조건 상태: 완료, 부분 확인, 미확인
- 원문이 최종 기준이라는 고지

`-`, 빈 박스, 임의 기본값만으로 누락을 표현하지 않는다.

## 6. 60초 진단 사용자 흐름

### 진입

- 정책 상세 사이드 패널에 `60초 정책 진단` 카드를 AI 리포트보다 위에 추가한다.
- 정책 목록 카드에 보조 행동 `60초 진단`을 추가한다.
- 카드 본문 클릭은 계속 정책 상세로 이동하고, 진단 버튼은 이벤트 전파를 막고 진단 화면으로 이동한다.
- 경로는 `/policies/:id/diagnosis`다.

### 입력

필수 입력은 다음과 같다.

- 사업 상태: `사업 중`, `사업 준비 중`
- 지역: 기존 17개 시·도 옵션
- 업종: 기존 정책 필터 업종 옵션
- 연 매출 구간: 사업 중일 때 필수
- 직원 수 구간: 사업 중일 때 필수

사업 준비 중이면 매출과 직원 수를 숨기고 `null`로 보낸다. 로그인 사용자의 사업 정보 조회에 성공하면 값을 미리 채우되 언제든 수정할 수 있다. 입력한 진단 정보는 첫 버전에서 저장하지 않는다.

### 처리 상태

제출 뒤 약 1.5초 동안 기존 로딩 스타일로 다음 세 단계를 순차 표시한다.

1. 내 사업 정보 확인
2. 공고문 조건 대조
3. 판정 근거 정리

실제 API 응답이 더 빠르더라도 전시에서 상태 변화가 인지되도록 최소 표시 시간을 둔다. API 오류 시 입력을 유지하고 재시도 버튼을 표시한다.

### 결과

결과 상단에는 다음만 강조한다.

- 판정: `신청 가능성 높음`, `조건 확인 필요`, `현재 대상 아님`, `판정 보류`
- 조건 일치도: 0~100점 또는 근거가 부족하면 점수 미표시
- 판정 신뢰도: 높음, 보통, 낮음
- 한 문장 요약

근거 표의 각 행은 다음 필드를 가진다.

- 항목명
- 내 조건
- 공고 조건
- 상태: `PASS`, `PARTIAL`, `UNKNOWN`, `FAIL`, `NOT_REQUIRED`
- 쉬운 한국어 이유
- 정보 출처

`UNKNOWN`은 오류가 아니라 중요한 결과다. 값이 없으면 성공으로 처리하지 않는다.

## 7. 판정 규칙

### 상태 의미

- `PASS`: 확인 가능한 사용자 값과 정책 값이 일치한다.
- `PARTIAL`: 사용자의 구간과 정책 기준이 일부 겹친다.
- `UNKNOWN`: 사용자 값 또는 정책 근거가 부족하다.
- `FAIL`: 확인 가능한 값이 정책 기준과 맞지 않는다.
- `NOT_REQUIRED`: 구조화된 공고에서 해당 조건이 요구되지 않음이 확인됐다.

구조화 정책 카드가 없는 경우 `조건 없음`과 `조건을 아직 모름`을 구분할 수 없으므로 `NOT_REQUIRED`가 아닌 `UNKNOWN`을 사용한다.

### 판정 등급

- `NOT_ELIGIBLE`: 마감 또는 명확한 지역 불일치처럼 hard fail이 있다.
- `ON_HOLD`: 안전한 비교에 필요한 정책 근거가 하나도 없다.
- `NEEDS_CONFIRMATION`: hard fail은 없지만 `FAIL`, `PARTIAL`, `UNKNOWN`이 있다.
- `LIKELY_ELIGIBLE`: 비교 대상 조건이 모두 `PASS` 또는 확인된 `NOT_REQUIRED`다.

표시 문구는 각각 `현재 대상 아님`, `판정 보류`, `조건 확인 필요`, `신청 가능성 높음`이다.

### 근거 우선순위

1. 사용 가능한 `PolicyCard.fullJson`의 구조화 필드
2. `Policy`의 지역, 업종, 신청 기간 메타데이터
3. 제목·설명·지원대상의 명확한 업종 표현은 PASS 보조 근거로만 사용
4. 근거가 없으면 UNKNOWN

본문에 업종 단어가 없다는 이유로 업종 불일치를 판정하지 않는다.

### 점수와 신뢰도

점수는 합격 확률이 아닌 조건 일치도다. 판정 가능한 조건과 UNKNOWN을 포함해 고정 가중치로 계산하고 `NOT_REQUIRED`는 분모에서 제외한다. 정책 카드가 없고 확인 가능한 근거가 두 개 미만이면 점수는 `null`이다.

- 지역 25
- 업종 25
- 신청 기간 15
- 사업 단계 15
- 매출 10
- 직원 수 10

상태 배율은 PASS 1.0, PARTIAL 0.5, UNKNOWN 0.3, FAIL 0.0이다.

- 높음: 추출 완료이며 UNKNOWN이 없다.
- 보통: 일부 조건이 확인되지 않았지만 세 항목 이상 비교됐다.
- 낮음: 정책 카드가 없거나 비교 가능한 항목이 두 개 이하이다.

## 8. API 계약

### 요청

`POST /api/v1/policies/{id}/diagnosis`

```json
{
  "businessStatus": true,
  "industry": "카페/음료",
  "region": "서울특별시",
  "annualRevenueBand": "5,000만원~1억원",
  "employeeCountBand": "1~4명"

```

인증 없이 호출할 수 있고 서버는 결과를 저장하지 않는다. 허용되지 않은 옵션과 사업 중인데 빠진 조건은 400으로 응답한다.

## 9. 체크리스트 정확성 교정

- 프론트는 정책 ID 1~12에서도 mock보다 API를 우선한다.
- API 실패 시 관련 없는 정책 mock으로 대체하지 않는다.
- 정책 카드가 없을 때 공통 서류는 `일반적으로 준비하면 좋은 서류`로 표시하고 필수 완료율 계산에서 제외한다.
- 기간이 없으면 `상시`라고 추정하지 않고 `기간 정보 없음 — 원문 공고 확인`으로 표시한다.
- 정책 카드에서 직접 확인된 문서만 `필수`로 표시한다.

## 10. 오류 및 빈 상태

- 정책 없음: 404와 정책 목록 복귀 행동
- 입력 오류: 해당 필드 아래 구체적인 오류
- 네트워크 오류: 입력 유지, 재시도, 원문 보기
- 카드 없음: 낮은 신뢰도와 UNKNOWN 표시
- 카드 파싱 실패: 판정 보류 또는 조건 확인 필요, 원문 링크 유지
- 신청 기간 종료: 현재 대상 아님과 hard fail 근거
- 신청 기간 없음: 상시 접수로 추정하지 않음
- AI 키 없음: 정책 상세와 진단은 정상 작동

## 11. 접근성과 상호작용

- 모든 입력은 가시적 label을 가진다.
- 상태는 색상뿐 아니라 텍스트와 아이콘으로 전달한다.
- 버튼은 키보드로 동작하고 focus 스타일을 유지한다.
- 로딩 중 제출 버튼을 비활성화한다.
- 결과 상단은 `aria-live="polite"`로 알린다.
- 애니메이션은 장식이며 결과 이해에 필수적이지 않다.

## 12. 테스트 및 완료 기준

### 백엔드

- 정책 카드 완전 일치
- 지역 불일치와 마감 hard fail
- 카드 없음, 파싱 실패, 부분 추출
- 매출·직원 구간의 PASS, PARTIAL, FAIL
- 잘못된 입력 400
- 외부 AI 호출과 DB 저장이 없음을 구조로 보장

### 프론트엔드

- 진단 요청 payload 생성과 준비 중 조건 처리
- 판정·상태 문구 매핑
- 정책 상세의 누락 필드 표시
- 체크리스트가 ID 1~12에서도 API를 우선
- TypeScript build와 ESLint

### 브라우저

- 정책 목록 → 상세 → 진단 → 결과 → 원문/체크리스트 흐름
- 로딩, 성공, 오류, 저신뢰도 상태
- 기존 헤더·여백·카드 스타일과의 시각적 일관성
- 콘솔 오류 없음

## 13. 금지 표현

- 합격률
- 확정 자격
- AI가 신청 가능 여부를 확정했다
- 원문에서 확인하지 않은 금액·조건·서류
- 기간 정보가 없을 때 `상시 접수`

항상 `조건 일치도`, `1차 진단`, `원문 최종 확인`을 사용한다.
